# LevelAuthoring

Переиспользуемые инструменты редактора Unity для создания комнат и наборов комнат из JSON. Код не зависит от FableRealm, R.E.P.O. или REPOLib. Можно перенести всю папку `Assets/LevelAuthoring` в другой проект с Built-in Render Pipeline.

Это библиотека **авторинга окружения**, не загрузчик карт для игры. Она создаёт обычные Unity-префабы, меши, материалы, обзорные сцены, рендеры и отчёты о геометрических проверках. Для игрового уровня остаётся привязка к API конкретной версии R.E.P.O.

## Добавление комнаты

1. Скопировать `Assets/FableRealm/RoomDefinitions/ExampleRoom.room.json` под новым именем.
2. Изменить `id`, материалы, элементы, контрольные точки и камеры. Идентификаторы: латиница, цифры, `_`, `-`.
3. Выделить JSON в Project и вызвать **Level Authoring → Build selected room recipe**.
4. Результат появится в `Assets/LevelAuthoringOutput/<id>`. Открыть `.unity`, изучить `.png` и `validation.txt`.

Никакой новый `case` в генераторе FableRealm не нужен. В текущем проекте подробная комната автоматически подменяет старую заготовку, если файл `RoomDefinitions/<room.key>.room.json` существует. Для HollowLibrary это уже подключено к общей сборке 24 комнат.

## Добавление набора комнат / будущего уровня

Создать `<name>.room-set.json`:

```json
{
  "schemaVersion": 1,
  "id": "NewRealm",
  "title": "New realm",
  "rooms": [
    {
      "recipe": "Assets/MyRooms/Hall.room.json",
      "role": "Normal",
      "difficulty": 1
    }
  ]
}
```

Выделить файл и вызвать **Level Authoring → Build selected room set**. Компилятор проверит все описания, соберёт каждую комнату и общую обзорную сцену. Число комнат не зафиксировано. Допустимые роли: `Start`, `Normal`, `Passage`, `DeadEnd`, `Extraction`; difficulty: 1–3. Роли пока записываются в контракт интеграции, а не регистрируются в REPOLib. Набор для просмотра может содержать только часть будущего уровня.

## Схема комнаты, версия 1

- `materials`: идентификатор, цвет HTML, smoothness, metallic, emission и grain. Grain создаёт повторяемую процедурную текстуру поверхности; это не готовая художественная PBR-текстура.
- `elements`: уникальные `id`, `kind`, `material`, локальные `position`, `rotation` в градусах, `size` в метрах, флаг `collider`.
- `anchors`: смысловые точки для проверок и последующего адаптера игры.
- `views`: позиции камер, цели и поле зрения для воспроизводимых рендеров.
- `seed`: определяет вариации книг. Повторная сборка одного рецепта даёт ту же геометрию.
- `bounds`: габарит для размещения комнат в обзорном наборе. Это не игровая зона и не автоматическое ограничение геометрии.

| kind элемента | Назначение |
|---|---|
| box | Стена, пол, перекрытие, мебель. Position — центр |
| arch | Арка: size.x — ширина, size.y — полная высота; radius — сечение |
| tube | Корень, балка, обод: points в локальных координатах, radius |
| disc | Круглый/овальный витраж в плоскости XY, двусторонний |
| shelf | Шкаф с книгами: origin на полу, count — число книжных рядов; palette[0] — отделка, остальные — обложки |
| stairs | Ступени вдоль +Z: size = ширина, подъём, длина; origin в центре по XZ на нижней высоте |
| rail | Ограждение вдоль X: size.x — длина, size.y — высота; count — число промежутков |
| light | Точечный свет: цвет из material, intensity, range, shadows |

У лестницы видимые ступени отделены от гладкого наклонного коллайдера. У шкафа коллизии есть на каркасе и полках, но не на каждой книге. Декоративные книги объединяются по материалу внутри шкафа. Проверка прохода под шкафом сама по себе не добавляется: такая ниша должна быть заложена в конкретном рецепте.

## Контракт интеграции

`room-definition.json` рядом с префабом сохраняет описание, включая anchors. В иерархии префаба точки находятся в `Integration anchors - not game components`. Пользовательских MonoBehaviour из Editor-сборки в префабах нет.

| Anchor kind | Смысл | Будущая привязка к R.E.P.O. |
|---|---|---|
| portal | Выход, направление наружу | Стыковка модулей и варианты закрытия |
| nav | Точка поверхности, connectsTo — двусторонние связи | LevelPoint и проверка NavMesh |
| volume | Центр и размеры объёма | RoomVolume и игровые слои |
| loot | Предлагаемое место ценности | ValuableVolume и ограничения добычи |
| hide | Точка внутри укрытия; +Z смотрит на заднюю стенку | Проверка обзора и размеров персонажа |
| pit | Верхняя контрольная точка, size.y — глубина | Падение, урон, возврат предметов |
| surface | Проверка наличия пола и высоты прохода | Дополнительный контроль геометрии |

**Адаптер игры ещё не реализован.** Ни наличие nav-точек, ни роль Extraction не создают автоматически навигацию монстров или экстрактор. Экспорт прямо помечен `AUTHORING ONLY`; не следует распространять его как готовую карту.

## Проверки и ограничения

### Проверка настоящего NavMesh

Рецепт может содержать `navigation` с полями radius, height, climb, slope, voxel, sampleDistance и maxVerticalSnap. В таком рецепте каждый элемент классифицируется полем `navigation`: `Walkable`, `Obstacle`, `Ignore`. Навигация запекается из физических коллайдеров встроенным модулем Unity AI; дополнительный пакет NavMeshSurface для редакторной проверки не нужен.

Сборка требует, чтобы все nav-точки находились рядом с поверхностью своего яруса, а каждое ребро имело полный NavMesh-путь. Авторские координаты не исправляются автоматически. Результаты: `navigation.asset`, геометрия поверхности `navigation-preview.asset`, JSON с углами маршрутов, текстовый отчёт и `navigation.png`. При общей сборке FableRealm подробные комнаты проходят эту проверку повторно.

`RoomNavigation.ValidateSeam` проверяет стык двух размещённых комнат на едином NavMesh. Он требует одинакового профиля, совпадающих выходов и встречного направления. Пример подключения библиотеки к залу корней находится в `LibraryShowcase.VerifySeam`. Это проверка конкретной пары, а не всей процедурной генерации.

Текущие размеры агента диагностические. Эти артефакты не подключаются автоматически к игровой сцене: игровой `LevelGenerator` строит навигацию отдельно, после расстановки модулей.

До сборки проверяются версия схемы, уникальность имён, материалы, типы элементов, геометрические параметры, корректность и связность графа навигации. В отдельной копии префаба проверяются пол, проходы, наличие настоящего провала, вход/задняя стенка укрытия и каждый участок маршрута с шагом около 0,25 м. Радиус пробы — 0,3 м; проверяемая высота — 1,75 м.

Это диагностические размеры, не подтверждённые размеры персонажа или тележки. Проверки не заменяют тесты с настоящими врагами, NavMesh, физикой ценностей и сетевой игрой. Loot/volume — метаданные, их игровая валидность не проверяется.

`FableRealm.Editor.LibraryShowcase.VerifyAll` проверяет пример и библиотеку, сборку набора, отказ на неизвестном типе элемента, отсутствующем материале и односторонней связи навигации. `FableRealm.Editor.FableRealmBuilder.BuildAndRender` дополнительно проверяет общий набор из 24 комнат.

## Сохранность ручной работы

Исходные JSON и Python-рецепт — редактируемые источники. Повторная сборка перезаписывает свои именованные материалы, меши, префабы, сцены, отчёты и рендеры в выходной папке. Ручные изменения делайте в копиях за её пределами. Удалённые из рецепта старые mesh-asset файлы автоматически не удаляются; они не попадают в новый префаб, но перед финальной упаковкой требуется очистка неиспользуемых ассетов.

## Версии и проверка

Целевой проект сохраняет Unity 6000.3.17f1, соответствующий локальной игре. Авторинг проверен в отдельной копии проекта с установленным Unity 6000.2.9f1. Игра в этих проверках не запускалась. Ассеты BluePrince в результаты не копировались: использован принцип разделения геометрии, коллизий и игровых данных.
